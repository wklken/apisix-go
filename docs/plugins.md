# APISIX 3.17 Plugin Support

> Current Go-native plugin status, supported behavior, and remaining compatibility boundaries.
>
> Official comparison baseline: Apache APISIX `release/3.17` (104 default plugins). Evidence is maintained against `pkg/plugin/init.go`, the plugin packages, route/proxy integration, focused tests, and the repository verification gate.
>
> Status audit: 2026-08-16. HTTP plugin request/response/streaming/protocol/log
> ownership is explicit for all 115 factory keys / 114 implementation identities;
> direct `Handler` compatibility paths are not installed by production routes.

## Summary

- Official APISIX 3.17 default plugins: **104**
- Registered default plugins: **100** (**96.2%**)
- Supported default plugins: **89** (**85.6%**)
- Deferred because of native/runtime or separate-subsystem boundaries: **9**
- Outside normal Go-native parity: **6**
- Additional documented rows: **14** (12 README/native extras and 2 registered non-default protocol entries)
- Total plugin rows in the status table: **118**

## Integrated plugin tests

The standalone integration suite under [`t/plugin`](../t/plugin/README.md) is
pinned to Apache APISIX commit
`c3d7d5ec69774121f53d2e20d29d09c816795dd7`. It contains 99 manifest files for
the 98 source-backed plugins marked Supported here plus supplemental
`redirect2`. Every manifest activates its target plugin in standalone resources
and passes the semantic coverage gate. Every scenario writes fresh
`config.yaml` and `apisix.yaml`, starts the real APISIX-Go CLI in standalone
YAML-provider mode, sends requests, and asserts the response, fixture request,
or startup log. External services are replaced by deterministic per-case
loopback fixtures, including TCP/TLS-TCP, UDP, gRPC, Redis, Kafka, Dubbo, and
LDAP protocol fixtures; no placeholder or skip reason is treated as coverage.

The four intentionally unregistered defaults are `ext-plugin-pre-req`, `ext-plugin-post-req`, `ext-plugin-post-resp`, and `inspect`. They require an external plugin runner or Lua/OpenResty runtime. The bounded `serverless-pre-function` and `serverless-post-function` compatibility implementations remain outside normal runtime parity.

## Status definitions

- **Supported:** registered, usable through the Go request/response pipeline, and covered by focused tests for important paths.
- **Supported (extra):** registered and tested, but outside the 104-default count.
- **Deferred (subsystem/runtime):** bounded behavior exists, but full parity still needs a separate transport, health, stream, or runtime contract.
- **Out of scope (runtime/native):** the official behavior depends on NGINX, OpenResty, Lua, an external runner, or TLS internals outside normal Go-native parity.
- **Estimated parity:** a manually maintained feature-parity estimate, not Go test coverage or converted upstream-corpus coverage.
- **Remaining jobs:** the highest-value compatibility boundary or monitor-only follow-up; implementation details remain in source and focused tests.

## Cross-plugin remaining work

These items require a new owner or runtime contract and should not be implemented as disconnected plugin-local work:

1. **General stream-plugin context:** define a stream context and lifecycle owner for every supported stream plugin, then add end-to-end fixtures. The current stream design is documented in [`design.md`](design.md).
2. **Upstream health-status API:** active/passive probe scheduling is cluster-owned; define persistence and `/v1/healthcheck` semantics before exposing state.
3. **Kafka external-broker smoke coverage:** add only when an external integration environment and credential-safe CI contract are available.
4. **Concrete expression, regex, or schema mismatches:** reproduce the APISIX-vs-Go mismatch first, then add the smallest regression and fix.

## Scope boundary

The following remain intentionally outside normal parity work: arbitrary Lua execution, `ngx_lua` APIs, exact OpenResty phase and body-filter timing, NGINX buffering and connection-state internals, OCSP/TLS stapling internals, exact shared-dict/lrucache/batch-manager behavior, OpenResty cosocket pooling, and external plugin-runner protocol compatibility.
